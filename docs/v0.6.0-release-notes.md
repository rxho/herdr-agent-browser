# Herdr Agent Browser v0.6.0 (experimental pre-release)

Conversation-level routing in a single long-running browser MCP process; **one Chrome**, with one shared default BrowserContext (cookies/localStorage shared) and separately pinned CDP targets for independent Claude conversations.

## Highlights

- Native `agent-browser mcp --tools core` proxy with per-call mapped `session`, rather than an MCP-startup-only `HAB_BROWSER_SESSION_ID`.
- Claude `PreToolUse` adapter injects the real Hook `session_id` and signs it with a short-lived HMAC proof bound to the tool name. MCP servers reject missing, expired or forged proofs. **Hook and MCP configuration remain opt-in; nothing is installed into Claude automatically.**
- Stable `(namespace, conversationId) → browserSessionId → CDP targetId` association, with per-conversation page and handoff state, no mutable current-session selector.
- Local-filesystem atomic lock serializes first-page allocation across MCP processes (and per-process single-flight prevents duplicate concurrent initialization).
- Viewer persists Session→target ownership by port and restores the **original** targets after Viewer restart. Interrupted handoff leases expire, never auto-resume.
- MCP restart / A→B→A / compaction / same-origin cookie sharing / independent DOM / concurrent invocations / A handoff while B works covered by automated checks including real Chrome E2E.
- Root and `HAB_BASE_PATH=/browser` deployments remain supported.

## Migration and compatibility

Existing v0.5.1 process-scoped MCP and Viewer setup remains available, and previously configured Agent settings are not modified. To use conversation-level routing, **the deployment owner must explicitly configure** two MCP entrypoints and the Claude `PreToolUse` Hook with an independently provisioned `HAB_CONVERSATION_SECRET_FILE` (mode 0600). See [conversation-scoped guide](docs/conversation-scoped-mcp.md) and [multi-session guide](docs/multi-session.md).

`agent-browser 0.39.2` uses Node.js 24+; the Viewer/plugin core remains Node 20+. The system never starts a separate Chrome for each conversation.

## Security and limitations

These are **cooperative session/Tab bindings**, not malicious-agent isolation: direct browser-level CDP access can bypass routing. OAuth popups are not automatically assigned. A restarted Chrome with changed target IDs is **not** silently re-adopted; deliberate recovery is required. A stale cross-process allocation lock is never automatically stolen. Shared account logout/localStorage mutations may affect all conversations. A correctly configured **trusted identity Hook is required**; tool arguments alone do not attest their source.

Validated on GitHub Actions with Node 22 unit tests and Node 24 real-Chrome MCP E2E. Not validated by changing any user's Claude configuration or deploying on their Mac.
